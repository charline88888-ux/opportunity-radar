## 2. 通用约定

- 日期：`YYYY-MM-DD`；周：ISO `YYYY-Www`；月：`YYYY-MM`；年：`YYYY`。全部按 Asia/Shanghai 日界。
- 评分：单维度 0–10，保留 1 位小数；总分为 0–100，保留 1 位小数。
- 数组：即使只有 1 个元素也用数组；空值用 `null`，不要用 `""` 混用。
- 枚举：所有 `*_id` / `*_ids` 必须存在于 `taxonomy.json`，引用完整性由 `scanner/validate.py` 强制校验（失败退出码非 0）。
- 证据：每条机会至少 1 条 `evidence`，优先 2–4 条来自**不同主体**的来源（三角验证）。`verified:true` 的项目要求所有证据 URL 在 v0.1.0 交付前实际可访问；打不开或无法确认的写 `verified:false` 并在 `compliance_notes` 说明。
- 免责：所有机会必须带 `disclaimer` 字段；不得出现"稳赚/保证/躺赚/内幕"等表述。

| `risks` | string[] | ✅ | 2–5 条，具体到触发条件 |
| `first_steps_7d` | string[] | ✅ | 3–6 条，7 天内可完成的验证动作 |
| `kill_criteria` | string[] | ✅ | 2–4 条，什么情况下放弃 |
| `compliance_notes` | string | ✅ | 合规提醒/需资质/版权/宗教敏感点 |
| `evidence_count` | int | ✅ | = `signal.evidence.length` |
| `activity_dates` | string[] | ✅ | 该机会历次"有新信号"的日期，升序，用于窗口归属 |
| `first_seen` | date | ✅ | 首次进入机会库日期 |
| `last_activity` | date | ✅ | `activity_dates` 最大值 |
| `momentum` | number | ✅ | 最近 30 天证据变化倍数，clip [0.5, 2.5]，1 位小数 |
| `rank_score` | number | ✅ | 排序分（公式见 5.2） |
| `tags` | enum[] | ✅ | 1–6 个 |
| `verified` | bool | ✅ | 证据 URL 是否已实际核验 |
| `disclaimer` | string | ✅ | 固定免责声明 |

### 4.5 `scores`

```json
{
  "dimensions": {
    "signal": 8.4, "gap": 7.8, "feasibility": 8.6, "economics": 8.2, "timing": 7.5,
    "competition": 6.5, "risk": 7.8, "fit": 8.0, "evidence": 7.6, "leverage": 6.8
  },
  "total": 78.9,
  "grade": "A"
}
```
公式（锁定）：
```
total = round_half_up( Σ(dimension_i × weight_i) × 10 , 1 )      # 四舍五入，非银行家舍入
rank_score = round_half_up( min(100, total × (1 + 0.12 × (momentum − 1))), 1 )
grade = S(≥85) / A(≥75) / B(≥65) / C(≥55) / D(<55)              # 用四舍五入后的 total 判定
```
`total` 与 `rank_score` 由扫描器重算，**必须与文件内数值一致**（validate.py 校验，允许 ±0.05 浮点误差）。

### 4.7 `window` 语义（v0.1.0 冻结前澄清，2026-10-22）

- `months_left`：**人工估算**的「仍可切入窗口」剩余月数，整数 **0–36**（0 仅用于 `closed`）。估算参考该机会**主信息差类型**的默认半衰期（平台 6 / 时间与渠道 9 / 价格 12 / 情绪 18 / 地理、语言、监管 18–24 / 认知、人口、文化 30–36）× 竞争与监管调整系数 0.5–1.0，再减去已过月数，向上取整。它是判断辅助，不是精确预测模型。
- `status` 判定（必须与 `months_left` 一致）：`open` = months_left ≥ 9；`peak` = 3–8；`closing` = 1–2；`closed` = 0。
- `decay`：`slow` = 半衰期 ≥ 24 个月的信息差主导；`medium` = 12–23；`fast` = < 12。
- v0.1.0 允许全部为 `open`（新库），但一旦填写 `peak/closing/closed` 必须满足上述映射；扫描器按此规则校验（V06 已覆盖合法性，V16 覆盖映射一致性）。

## 5. `rankings.json` —— 唯一权威榜单

### 5.1 结构

```json
{
  "meta": { "data_version": "0.1.0", "as_of": "2026-10-22", "generator": "scanner/pipeline.py", "window_rules": "day=last_activity==as_of; week=ISO week; month=YYYY-MM; year=YYYY" },
  "windows": {
    "day":   { "key": "2026-10-22", "label": "2026年10月22日", "items": [ { "opp_id": "opp-…", "rank": 1, "rank_score": 82.1, "total": 79.0, "delta": 2, "change": "up" } ] },
    "week":  { "key": "2026-W43", "label": "2026年第43周", "items": [] },
    "month": { "key": "2026-10",  "label": "2026年10月", "items": [] },
    "year":  { "key": "2026",     "label": "2026年", "items": [] }
  }
}
```
- 窗口归属：`day` = `last_activity == as_of`；`week` = `last_activity` 落在当前 ISO 周；`month` / `year` 同理。同一机会可同时出现在多个窗口。
- 各窗口按 `rank_score` 降序，同分依次按 `momentum` 降序、`evidence_count` 降序、`last_activity` 降序、`opp_id` 升序兜底，`rank` 从 1 连续。
- `delta` 口径（v0.3.0）：优先用「上一份历史快照的同窗口名次」对比——`delta = 上期名次 − 本期名次`（正数=上升），`delta_basis="history"`；上一份快照可以是真实每日快照（`reconstructed=false`）或历史回放快照（`reconstructed=true`，仅用于补足演示/对照，UI 明示）。窗口对比：day 取上一日快照的 day 窗口；week/month/year 取相同窗口 key 的上期快照。若没有可比历史（首版或该窗口上期为空）则回退 v0.1.0 的「相邻更大窗口」口径（day←week、week←month、month←year、year 无参照），`delta_basis="adjacent-window"`；完全无参照时 `delta:null, change:"new"`。`change ∈ {new, up, down, flat}`，与 delta 符号一致（delta>0→up、<0→down、=0→flat）。
- `rankings.json.meta` 必含：`delta_basis`（本文件整体口径：`history` / `adjacent-window`）、`history_as_of`（上一快照日期或 null）、`tie_breaker`（排序链说明）。
- 榜单规模（v0.6.0）：`day` ≥ 10 条，`week` ≥ 20 条，`month` ≥ 30 条，`year` = 全部（≥ 80 条）。**数据工程必须按此配额布置 `last_activity` 日期**（当天 2026-10-22 至少 6 条）。

### 5.2 计算规则（扫描器实现）

1. 读取 `opportunities.json`，对每条重算 `total` 与 `rank_score`（公式见 4.5），与文件值不一致时以计算值为准并告警。
2. 按窗口规则分组、排序、编号。
3. 写 `rankings.json` 与 `stats.json`。`stats.json` 至少包含：
   `{"kpi":{"total_opps","new_today","grade_a_plus","industries_covered","regions_covered","avg_total"},"by_industry":[…],"by_gap_type":[…],"by_region":[…],"by_need":[…],"score_histogram":[0-10,…],"trend_14d":[{"date","new_count","avg_score"}],"open_window_value_cny":…}`

## 10. 版本与变更流程

1. 字段增删、枚举调整、公式变化 = **数据契约变更**，必须：升 `data_version`（0.1.x 补丁 / 0.2.0 结构变更）→ 更新本文件 → 更新 `data/CHANGELOG.md` → 通知 Lead、前端、红队 → 前端重新构建。
2. 只新增机会、不改结构 = 补丁版本（如 `0.1.1`），仍需写 CHANGELOG。
3. 应用版本与数据版本独立：应用升级不要求数据升级；数据升级需重跑 `scanner/pipeline.py --all` 并重新构建前端。
4. 旧版本 `releases/` 目录只读，**永不修改**（详见 `docs/10-版本与发布管理.md`）。

---

## 11. 前后端对接约定

- 前端构建前执行 `node scripts/sync-data.mjs`（在 `app/` 内），把 `../data/*.json` 复制到 `app/src/data/`，前端只 import 该目录；`app/src/data/` 被 gitignore，不产生第二份手工数据。
- 前端**不重新计算榜单窗口归属**，只读 `rankings.json`；但机会详情页允许"自定义权重重算总分"作为交互演示，其计算必须与 4.5 公式一致，并标注"演示：权重可调"。
- 前端不依赖任何 CDN/外网资源，构建产物 `base: './'`，路由使用 HashRouter，保证 `file://` 双击可打开。
- 数据缺失或字段为空时，前端必须有降级展示，不得白屏。

---

## 12. 数据伦理与免责

- 只收集公开信息；不抓取个人信息、不绕过登录/付费墙、不违反平台 ToS；`compliance:red` 的源只允许人工浏览。
- 证据必须可回溯到 URL；禁止编造数据、伪造评论、夸大规模。无法验证就写 `verified:false`。
- 每个机会页必须展示免责声明；涉及金融、医疗、法律、宗教、跨境合规的机会必须给 `compliance_notes`。
- 机会库是"假设池"而非常识：任何一条在使用前都要用 `first_steps_7d` 做最小验证。
